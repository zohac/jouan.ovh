# Direction stratégique du site

Le site ne doit plus être un **portfolio personnel généraliste**.

Il doit devenir une **landing page commerciale de développeur freelance Full Stack TypeScript**, conçue pour faire passer un visiteur par ce chemin :

> **Je comprends ce qu’il fait → je vois qu’il l’a déjà fait → je crois qu’il peut résoudre mon problème → je le contacte.**

La nouvelle version doit donc être pensée comme un **outil de conversion**, pas comme une vitrine exhaustive de carrière.

---

# Positionnement central

Le message principal doit être :

> **Développeur Full Stack TypeScript spécialisé Nuxt / NestJS pour applications web et SaaS.**

Tout le site doit renforcer cette idée.

Pas :

- développeur web polyvalent ;
- WordPress ;
- consultant IA ;
- QA ;
- automatisation ;
- CTO ;
- créateur de SaaS ;
- entrepreneur.

Toutes ces choses peuvent être vraies, mais elles ne doivent pas devenir des portes d’entrée concurrentes.

La hiérarchie doit être :

**Full Stack TypeScript**  
→ **Nuxt / NestJS**  
→ **applications web / SaaS**  
→ **culture produit**  
→ **QA / qualité**  
→ **IA comme avantage supplémentaire**

---

# Pourquoi ce repositionnement

Le site actuel souffre surtout d’un problème de **dispersion**.

Aujourd’hui, il mélange plusieurs promesses :

- WordPress ;
- développement web ;
- IA ;
- automatisation ;
- QA ;
- développement applicatif.

Le visiteur doit faire lui-même le travail pour comprendre ce que Simon vend réellement.

C’est mauvais pour la conversion.

Un prospect ne cherche pas à comprendre toute une carrière. Il cherche à répondre très vite à :

> **“Est-ce que cette personne correspond à mon besoin ?”**

Le nouveau site doit donc volontairement devenir **moins exhaustif**, mais beaucoup plus clair.

---

# Objectif business

Le site doit aider Simon à décrocher des missions comme :

- développement de SaaS ;
- développement d’applications métier ;
- création de MVP ;
- frontend Nuxt ;
- backend NestJS ;
- développement Full Stack TypeScript ;
- évolution d’une application existante ;
- reprise d’un produit ;
- intégration API / Stripe / auth / base de données ;
- architecture d’applications web.

Le site ne doit pas être optimisé prioritairement pour attirer :

- WordPress ;
- petits sites vitrines ;
- maintenance PHP legacy ;
- QA pure ;
- tests manuels ;
- automatisations no-code ;
- missions génériques “IA”.

Même si Simon peut les réaliser.

---

# Cible principale

Le site doit parler à :

- fondateurs de startup ;
- CTO ;
- tech leads ;
- product managers ;
- dirigeants de PME avec un besoin applicatif ;
- éditeurs SaaS ;
- équipes produit avec backlog et manque de capacité.

Le ton doit donc donner une impression de :

- autonomie ;
- maturité ;
- capacité à comprendre le produit ;
- capacité à prendre un sujet de bout en bout ;
- fiabilité.

---

# Transformation du site

La refonte ne doit pas seulement être graphique.

Elle doit surtout transformer le site de :

> **“Voilà qui je suis et tout ce que je sais faire.”**

en :

> **“Voilà les problèmes que je peux résoudre pour vous et les preuves que je l’ai déjà fait.”**

C’est le changement le plus important.

---

# Hero

Le hero doit être extrêmement simple.

Il doit répondre en quelques secondes à :

### Qui ?

Développeur Full Stack TypeScript.

### Spécialité ?

Nuxt / NestJS.

### Pour quoi ?

Applications web et SaaS.

### Pour qui ?

Startups, PME, équipes produit.

### Action ?

Discuter d’un projet.

Exemple de direction :

> **Développeur Full Stack TypeScript**
>
> Je conçois et développe des applications web et SaaS avec Nuxt, NestJS et PostgreSQL.
>
> De l’architecture au déploiement, j’interviens sur des produits neufs comme sur des applications existantes.
>
> **[Discuter de votre projet]**

Pas besoin d’une punchline abstraite.

---

# Ne plus faire de WordPress un service principal

C’est un des changements majeurs.

WordPress peut rester mentionné quelque part dans le parcours ou les anciennes expériences.

Mais il ne doit plus apparaître comme une offre commerciale de premier niveau.

Pourquoi ?

Parce que le mot **WordPress** attire un marché complètement différent de celui recherché :

- budgets plus bas ;
- projets plus simples ;
- attentes différentes ;
- concurrence différente ;
- perception plus “agence web / site vitrine”.

Cela affaiblit directement le positionnement SaaS / Full Stack TypeScript.

---

# Services

Il faut peu de services.

Trois maximum.

## 1. Création d’applications web et SaaS

De l’idée à une application fonctionnelle.

Frontend, backend, base de données, authentification, paiements, API.

## 2. Développement Full Stack TypeScript

Nuxt / Vue côté frontend.

NestJS / Node côté backend.

PostgreSQL côté données.

## 3. Évolution d’applications existantes

Nouvelles fonctionnalités, refactoring, intégrations, qualité, architecture.

L’IA et la QA peuvent être intégrées dans ces offres comme avantages.

Pas comme deux nouveaux services indépendants.

---

# Preuves avant discours marketing

Le site doit privilégier les **preuves**.

La meilleure preuve actuelle est Keova.

Puis TryOn.

Puis Kidizz.

Puis Nodium.

Le site doit montrer :

> **Simon ne dit pas simplement qu’il sait construire des SaaS. Il en construit réellement.**

---

# Keova doit devenir la pièce maîtresse

Keova doit être présenté comme **case study principal**.

Pas uniquement avec une capture et une stack.

Il faut expliquer :

- le besoin ;
- le produit ;
- le rôle de Simon ;
- l’architecture ;
- les problèmes techniques ;
- les fonctionnalités ;
- les décisions ;
- le résultat.

Le prospect doit pouvoir se dire :

> “Mon projet ressemble à ça. Il saurait probablement le faire.”

C’est beaucoup plus puissant qu’une liste de technologies.

---

# TryOn comme deuxième cas d’étude

TryOn doit montrer une autre facette :

> Full Stack + produit + intégration d’IA générative.

Il permet de démontrer que Simon peut manipuler :

- API d’IA ;
- orchestration ;
- workflows asynchrones ;
- génération d’images ;
- produit SaaS.

C’est une preuve de complexité technique supplémentaire.

---

# Nodium comme preuve prospective

Nodium ne doit pas être présenté comme un produit fini.

Il doit apparaître comme :

> **Projet en cours / laboratoire technique**

et montrer :

- agents IA ;
- architecture agentique ;
- local/cloud ;
- orchestration ;
- permissions ;
- outils ;
- mémoire ;
- runtimes.

Il sert surtout à démontrer que Simon maîtrise les évolutions récentes de l’engineering IA.

---

# QA : différenciateur, pas offre principale

L’expérience QA doit être conservée.

Mais le message doit devenir :

> **Je suis un développeur Full Stack avec une forte culture de qualité logicielle.**

Cela permet de valoriser :

- tests ;
- automatisation ;
- fiabilité ;
- cas limites ;
- parcours critiques ;
- maintenabilité.

Le visiteur ne doit jamais hésiter entre :

> “Est-ce un QA ?”

et :

> “Est-ce un développeur ?”

La réponse doit être immédiate :

> **Développeur Full Stack, avec une expertise QA rare.**

---

# IA : levier, pas identité principale

Même logique.

L’IA doit apparaître comme un accélérateur et une expertise moderne.

Exemples :

- agents de développement ;
- code review assistée ;
- génération et analyse de tests ;
- intégration LLM ;
- workflows agentiques ;
- automatisation.

Mais éviter :

> Expert IA

ou :

> Consultant IA

en positionnement principal.

Sinon le site repart immédiatement dans la dispersion.

---

# CTA

Le CTA doit être orienté mission.

Bon :

> **Discuter de votre projet**

> **Parlons de votre application**

> **Me contacter pour une mission**

Moins bon :

> Découvrir mon univers

> Explorer mes projets

> Voir mon GitHub

Ces actions peuvent exister, mais pas comme CTA principal.

---

# Réduire le nombre de décisions

Pour convertir, il faut limiter les choix.

La navigation peut rester très simple :

**Accueil**  
**Projets**  
**À propos**  
**Contact**

Éventuellement :

**Services**

Mais éviter une dizaine de sections et sous-pages.

---

# Rôle de la page À propos

La page À propos ne doit pas être un CV.

Elle doit expliquer pourquoi le parcours de Simon en fait un meilleur développeur.

Narratif possible :

**Métrologie**  
→ rigueur

**Développement web**  
→ expérience technique

**QA**  
→ culture qualité

**SaaS**  
→ vision produit

**IA**  
→ engineering moderne

Le parcours doit converger vers le positionnement actuel.

---

# Design

Le design actuel orienté dev/terminal peut être conservé.

Il correspond plutôt bien au profil technique.

Mais il ne doit pas prendre le dessus sur le message.

La priorité est :

**Clarté > esthétique > effets**

Un site techniquement impressionnant mais commercialement ambigu serait un échec.

---

# Niveau de langage

Éviter le jargon dans le hero.

Un CTO comprendra NestJS.

Un dirigeant de PME, pas forcément.

Il faut donc mélanger :

> **Applications web et SaaS**

avec :

> **Nuxt / NestJS / TypeScript**

Le besoin avant la techno.

# SEO

Le site doit progressivement cibler :

- développeur Full Stack TypeScript freelance ;
- développeur Nuxt freelance ;
- développeur NestJS freelance ;
- développeur SaaS ;
- développement SaaS ;
- développeur Node.js freelance ;
- développeur Vue.js freelance ;
- développement application métier.

Mais le SEO ne doit pas dégrader les textes.

---

# Perception recherchée

Après 5 secondes :

> **Développeur Full Stack TypeScript / Nuxt / NestJS.**

Après 30 secondes :

> **Il construit des SaaS complets et semble très autonome.**

Après deux minutes :

> **Il a une vraie culture produit, une grosse expérience qualité et maîtrise aussi très bien l’IA.**

Après consultation des projets :

> **Je pourrais lui confier mon produit.**

C’est cette progression qui doit guider toute la refonte.

---

# Ce qu’il faut volontairement sacrifier

La refonte doit accepter de moins mettre en avant certaines choses.

Notamment :

- WordPress ;
- PHP ;
- Symfony ;
- Prestashop ;
- Drupal ;
- no-code ;
- automatisation générique ;
- QA comme prestation autonome ;
- toutes les technos historiques.

Ce n’est pas nier l’expérience.

C’est **choisir ce que l’on veut vendre aujourd’hui**.

# Principe directeur pour l’agent IA

Tu peux lui donner cette instruction telle quelle :

> **Ne conçois pas le site comme un portfolio exhaustif de Simon. Conçois-le comme un funnel commercial destiné à transformer un prospect recherchant un développeur Full Stack TypeScript en prise de contact. Chaque section doit soit clarifier son positionnement, soit fournir une preuve, soit réduire un doute, soit pousser vers le contact. Si un élément ne remplit aucune de ces fonctions, il est probablement inutile.**

Et la règle finale :

> **Le site et Malt doivent raconter exactement la même histoire : développeur Full Stack TypeScript spécialisé Nuxt/NestJS, capable de construire et faire évoluer des applications web et SaaS de bout en bout, avec comme différenciateurs une forte culture produit, QA et IA.**
